Part one

The map

The framework separates things every product shares from things one product needs. That split is the whole architecture — get it right and adding a second product costs one config entry.

├─ playwright.config.js generates projects, picks the instance
├─ .env.test / .qa / .uat / .prod one per environment, same variable names
│
├─ src/config/
│ └─ environments.js which instance, which URL, which credentials
│
├─ src/core/ shared by every product — edit rarely
│ ├─ base-page.js click / fill / waitForVisible helpers
│ ├─ fixtures/ env injection, production guard
│ ├─ testlink/results.js Playwright results → TestLink payload
│ └─ utils/test-data.js unique emails, dates, names
│
└─ src/projects/loyaltri/ everything Loyaltri-specific
├─ auth.setup.js logs in once per run
├─ pages/ Page Objects — where locators live
├─ data/ non-secret fixtures and expected messages
└─ tests/ui/ · tests/api/ the specs themselves

The one rule

Locators live in pages/. Assertions live in tests/. A spec should read like a test plan — go here, do this, expect that — with no CSS selectors in sight. When the UI changes you fix one Page Object, not fifteen specs.

Part two

Adding a test case

This is a real sequence — each step depends on the one before it. Follow it in order and a new case takes about twenty minutes.

  1. Write the case in TestLink first

    TestLink → your suite → Create test case

    Write it as a manual case with proper steps and expected results, then note the external ID it gets — LOYTRI-52, LOYTRI-53 and so on. TestLink assigns this; you never invent it.

    Writing the case first forces you to decide what "correct" actually means before you write code that asserts it. Automating first tends to produce a test that just describes whatever the app currently does.

  2. Record the flow

    npm run codegen -- https://alpha.loyaltri.com

    Click through the flow in the recorder. The output is throwaway — it exists to capture real locators and real button labels, not to become the test.

    PowerShell
    npm run codegen -- https://alpha.loyaltri.com

  3. Turn the recording into a Page Object

    src/projects/loyaltri/pages/

    Codegen produces brittle selectors. Rewrite them as roles and labels, and give each scenario a named method.

    before — codegen output
    page.locator('a').filter({ hasText: 'AAdmin Loyaltriadmin@loyaltri' })
// hardcodes one user's name — breaks for everyone else
    after — LoginPage.js
    this.accountMenu = page.locator('a')
  .filter({ hasText: /[\w.+-]+@[\w-]+\.[\w.]+/ }).first();
// matches any signed-in user by email pattern

    Name methods after the scenario, not the mechanics: loginWithRememberMe(), cancelLogout(), requestPasswordReset().

  4. Write the spec and tag it

    src/projects/loyaltri/tests/ui/smoke/

    The title mirrors the TestLink case name, and carries the external ID as a tag. That tag is the entire integration.

    login.spec.js
    test('TC01 — Successful login with valid credentials @LOYTRI-37', async ({ page, env }) => {
  const login = new LoginPage(page);

  await login.goto();
  await login.login(env.username, env.password);

  await expect(login.accountMenu).toBeVisible();
});

    Import test and expect from core/fixtures/test-fixtures, never from @playwright/test directly — that is what injects env and applies the production guard.

    Tag rules

    A case tag is @LOYTRI-52 — uppercase letters, dash, digits. Ordinary tags like @smoke and @no-prod are deliberately ignored by the matcher, so they can never be mistaken for a case ID.

    Any test that creates or changes records must also carry @no-prod.

  5. Prove it runs

    npm run test:test

    Run just your new case by its tag, watch it in a real browser, then run the whole file to check you haven't broken a neighbour.

    PowerShell
    # just the new case, visible browser
npm run test:test -- --grep "@LOYTRI-52" --headed

# the whole login file
npm run test:test -- login.spec.js

Part three

How TestLink is integrated

One tag in the test title does two jobs: it selects what runs, and it addresses where the result goes. There is no mapping file to maintain, because a mapping file drifts and a tag in the title cannot.

Step 1 · TestLink Assign A tester is assigned cases inside a Test Plan and Build. That assignment is the input.
Step 2 · Framework Select Assigned IDs become a grep: @LOYTRI-37\b|@LOYTRI-40\b — only those tests run.
Step 3 · Playwright Execute Runs against the chosen instance and writes reports/<env>/results.json.
Step 4 · Framework Read Results are flattened to one record per case: status, duration, error, screenshot.
Step 5 · TestLink API Publish Each record posts to the case's execution record with notes attached.
Step 6 · TestLink Report The Build shows pass / fail / blocked per case, per tester.

Dashed borders mark the two steps that are written but not yet connected — see what's blocked.

Status mapping

Playwright outcomes translate to TestLink execution codes. The important one is the third row.

PlaywrightCodeTestLinkWhy
passedpPassedAssertions held.
failed / timedOutfFailedError message and failure screenshot go into the notes.
skippedbBlockedIt never ran — which is not the same as passing. Reporting a skip as a pass would be a lie in the audit trail.
Retries

Only the final attempt is reported. A test that fails then passes on retry is a pass; the retry count is kept so the notes can flag it as flaky.

Test Plans and Builds — the part people miss

A test case is a template. You never execute it directly. You execute it inside a Build, which lives inside a Test Plan — and that is the only place an assignment can exist.

LevelWhat it isHow often you make one
Test ProjectLoyaltriOnce, ever
Test SuiteLogin Test, Employee Onboarding — where cases are writtenPer feature area
Test PlanA chosen subset of cases for one round of testingPer cycle or release
BuildWhat you actually execute against; results attach herePer deployment
AssignmentCase → tester, inside a BuildPer cycle

To set one up: Test Plan Management → Create, then Add / Remove Test Cases, then Builds/Releases → Create, then Assign Test Case Execution. Each tester generates their own key under My Settings → Generate a new API key, so TestLink records who really ran what.

Part four

Running tests

Every run answers two questions: which environment, and which tests. The environment is the npm script. The tests are the flags after --.

Choosing the environment

All four .env files use identical variable names, so nothing in the code knows which instance it is hitting. Only the values change.

CommandReadsTargets
npm run test:test.env.testalpha.loyaltri.com
npm run test:qa.env.qaQA instance
npm run test:uat.env.uatUAT instance
npm run test:prod.env.prodProduction — read-only tests only

Every run prints its target before doing anything, because the most expensive mistake here is not knowing which server you just tested:

npm run test:uat
  Playwright target instance: UAT  (.env.uat)

Running 15 tests using 2 workers
  ✓ TC01 — Successful login with valid credentials @LOYTRI-37   12.7s
  ✓ TC02 — Successful login with Remember Me ticked @LOYTRI-38   8.6s
  …
  15 passed (2.2m)

Choosing what runs

Add after --Runs
--grep "@LOYTRI-37"One specific TestLink case
--grep "@smoke"The smoke set
--grep "@regression"The regression set
--project=loyaltri-uiBrowser tests only
--project=loyaltri-apiAPI tests only, no browser

combining them
# the smoke set on UAT, in a visible browser
npm run test:uat -- --grep "@smoke" --project=loyaltri-ui --headed

# three assigned cases on QA
npm run test:qa -- --grep "@LOYTRI-37\b|@LOYTRI-40\b|@LOYTRI-46\b"

Reading the report

Reports are kept per environment, so a UAT run never overwrites the QA results you were about to read.

PowerShell
npm run report:qa      # opens reports/qa/html-report
npm run report:uat

The HTML report holds the failure screenshot, a video, and a trace you can step through frame by frame. For a failure you cannot reproduce, the trace is the first place to look.

Production guard

Any test tagged @no-prod is skipped automatically when the target is production, and reported as blocked with the reason. Read-only tests still run, so prod stays useful for smoke checks.

Overriding it is deliberate and explicit: npm run test:prod:unsafe. Onboarding tests create real employee records in the live HRMS — nobody cleans those up.

Part five

Four Loyaltri quirks that will bite you

These were all found by running against the live app. They are handled in the framework already — this is so you recognise them when writing a new test rather than losing an afternoon.

1 · The URL never changes

Loyaltri is a single-page app serving both the login form and the dashboard from /. expect(page).toHaveURL(/dashboard/) can never pass. Prove a session with login.accountMenu or dashboard.topBar instead.

2 · Saved sessions get wiped

The app enforces a single-tab session and deletes its own auth keys when a session is restored into a fresh browser. Playwright never persists sessionStorage, so every reused login looked valid and then silently signed itself out. The fix is sessionStorageSeed in environments.js, which reseeds two keys before app code runs. Leave it alone.

3 · Error messages are transient

Sign-in failures and reset confirmations are toasts that vanish after a few seconds. Assert on them immediately after the action — no slow steps in between.

4 · The sidebar is invisible to Playwright

The left module rail renders as <aside class="sidebar hidden lg:block close"> — present in the DOM but display:none at every width tested, up to 1920px. Never assert it is visible; anything navigating it must expand it first.

Also worth knowing

The dashboard greeting is randomised — "Hey", "Hi", "It's great to see you again". Never assert on it. And "Welcome back" belongs to the login page, so matching it would pass against a signed-out browser.

The blocker — a server fix, not a code fix

TestLink's API cannot load. PHP fails to parse the file, so both XML-RPC and REST return errors while the web UI works normally. No API setting can work around a parse error.

the error
Parse error: syntax error, unexpected '$this' (T_VARIABLE)
in /var/www/html/lib/api/xmlrpc/v1/xmlrpc.class.php on line 3557

# for whoever administers the server — confirms it without a web server:
php -l /var/www/html/lib/api/xmlrpc/v1/xmlrpc.class.php

Server is nginx 1.24 on Ubuntu, PHP 7.4.33, TestLink 1.9.20. Replacing that one file from a clean 1.9.20 archive is the likely fix — the rest of the install is healthy. Once php -l reports No syntax errors detected, the two dashed steps in Part three connect and results start flowing automatically.

Until then

Everything else works. Run your assigned cases with --grep, read the pass/fail from the terminal, and record the results in TestLink by hand. The only manual step is the last one.
